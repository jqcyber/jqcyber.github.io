Overview

T-Pot is an all-in-one honeypot platform from Deutsche Telekom Security. It bundles over 20 honeypot daemons, including Cowrie, Dionaea, and Honeytrap, into a single Docker-based deployment that exposes many fake services for attackers to hit.

I deployed T-Pot in a controlled environment, exposed it to the internet, and collected real attack data, including brute-force attempts, credential stuffing, malware drops, and exploitation attempts.

Objectives

  • Deploy and configure T-Pot on a Linux host exposed to the internet
  • Collect live attack telemetry from real-world threat actors
  • Analyze attacker TTPs, source IPs, payloads, and credentials attempted
  • Build familiarity with threat intelligence collection and log analysis
  • Explore the Kibana dashboards built into T-Pot for visual threat analysis

Tools & Environment

I deployed T-Pot across two Azure virtual machines in a Hive/Sensor architecture. The Hive handles management and visualization, and the Sensor runs the honeypots. Splitting the roles keeps the logs and dashboards off the machine attackers can reach.

  • T-Pot: multi-honeypot platform (Docker-based)
  • Microsoft Azure: cloud hosting for both VMs
  • Linux: host OS for both the Hive and Sensor
  • Docker / Docker Compose: container orchestration
  • Kibana: built-in visualization and log analysis dashboard
  • Elasticsearch: log storage and indexing backend
  • Cowrie: SSH/Telnet honeypot for credential capture
  • Dionaea: malware capture honeypot

Deployment Process

Important: T-Pot is exposed to the internet on purpose. Deploy it on a dedicated, isolated host, never on a machine with access to sensitive data or production networks. A honeypot can itself be compromised, and running one on a home network draws malicious traffic toward everything else on that network. Use a cloud VM.

T-Pot uses a distributed Hive/Sensor architecture. The Hive is the central management and visualization node, running Elasticsearch, Kibana, Logstash, and the web UI. The Sensor runs the honeypot daemons and ships all captured log data back to the Hive over an encrypted SSH tunnel.

Step 1: Provision Azure VMs

I provisioned two Azure VMs, the Hive (16 GB RAM, 256 GB SSD) and the Sensor (8 GB RAM, 128 GB SSD), each on a clean Linux install. Both sat on public subnets with no inbound firewall rules blocking honeypot ports, so attacker traffic could reach the Sensor. I restricted management access to a non-default SSH port.

Step 2: Install T-Pot on the Hive

On the Hive VM, I ran the T-Pot installer as a non-root user and chose H (Hive) at the installation-type prompt. That option installs the full Elastic Stack, an NGINX reverse proxy, the Kibana dashboards, the GeoIP Attack Map, and the management tools.

bash: Hive installation 
# Run as a non-root user from $HOME
env bash -c "$(curl -sL https://github.com/telekom-security/tpotce/raw/master/install.sh)"

# Select H for Hive when prompted
# Set a WEB_USER and password for the T-Pot WebUI (BasicAuth)
# Installer will configure Docker, Logstash, Kibana, NGINX, and reboot

When the installer finishes, the Hive reboots. T-Pot moves the system SSH port to 64295 so Cowrie can listen on port 22. After the reboot, the Kibana dashboard and Attack Map are at https://<hive-ip>:64297.

Step 3: Install T-Pot on the Sensor

On the Sensor VM, I ran the same installer and chose S (Sensor). The Sensor gets only the honeypot daemons and the Logstash forwarder, with no Kibana or Elastic Stack. It stays inactive until it is linked to the Hive in the next step.

bash: Sensor installation 
# Run on the Sensor VM as a non-root user from $HOME
env bash -c "$(curl -sL https://github.com/telekom-security/tpotce/raw/master/install.sh)"

# Select S for Sensor when prompted
# Reboot once installation completes

Step 4: Connect the Sensor to the Hive

Once both VMs are up, the Sensor needs a link to the Hive to forward its logs. Running deploy.sh on the Hive generates SSH keys and sets up an encrypted Logstash tunnel between the two nodes.

bash: linking Sensor to Hive 
# On the Hive, generate an SSH key for the Sensor connection
ssh-keygen # leave passphrase empty

# Deploy the Sensor from the Hive
cd ~/tpotce
./deploy.sh # follow prompts: enter Sensor IP and credentials

# Verify all containers are running on both nodes
dps.sh

After linking, the Sensor sends honeypot events to the Hive's Elasticsearch over an SSH tunnel on port 64295. The Hive account created for this connection can only forward logs and cannot open an interactive shell.

Step 5: Verify and monitor

With both nodes running, honeypot data reaches Kibana in real time. The T-Pot landing page at https://<hive-ip>:64297 links to the Kibana dashboard, GeoIP Attack Map, CyberChef, Elasticvue, and SpiderFoot, all preconfigured.

Results & Findings

Attacks started shortly after the honeypot went live. In the first 24 hours it logged over 5,000 attacks, and most of them hit Cowrie, the SSH honeypot.

In the SSH brute-force data, the most common username was root and the most common password was 123456. Attackers led with default and weak credentials.

Notable: 99% of source IPs were already flagged as malicious in threat intelligence databases, which suggests most of this traffic comes from known botnets and repeat scanners.

The Kibana dashboard breaks the telemetry down by origin country, targeted port, attacker IP, and attempted credentials.

Key finding: Most attacks went to Cowrie and used weak, common credentials. On this honeypot, attackers relied on automated scanning and known credential lists, not custom techniques.

Lessons Learned

  • Scanning starts right away: internet-facing systems get found and probed almost as soon as they go live
  • Attackers try weak credentials first: root/123456 was the most attempted username and password pair
  • Most attackers were already known: 99% of source IPs were already in threat intel databases, so an IP reputation feed would have flagged nearly all of them
  • SSH draws the most attacks: most traffic went to Cowrie, so SSH is the first service to harden on an internet-facing host
  • Host honeypots in the cloud: Azure VMs kept the honeypot off my own network and away from other systems
  • Dashboards speed up analysis: Kibana summarized thousands of log lines by country, port, IP, and credential
